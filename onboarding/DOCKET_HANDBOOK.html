Part I

Foundations

What the system is for, the single constraint that dictated its shape, and the map of its parts.

01What Docket is

The product in one page

Docket takes a Jira ticket and walks it through a nine-stage pipeline. Each stage is performed by an AI model working from a written brief, and each stage ends at a checkpoint that ordinary Python code has to be satisfied with before the next stage may begin. Everything that happens is written to an append-only database, and every screen you can open is a read-only view of that database.

The pipeline mirrors what a careful team already does by hand: understand the ticket, map the codebase, plan, specify tests, implement, review, security-scan, QA, and mutation-test.

The actual goal

Docket is not primarily trying to reproduce work a human already shipped, only faster. It brings two things that manual development usually does not bring to every ticket: mutation testing, and a QA agent that never gets tired or optimistic.

So its real value is finding bugs in code that already shipped. The prize verdict is DOCKET_FOUND_IT, and the metric that matters long-term is confirmed defects per run — not pass rate, and not tickets completed.

The sentence the whole architecture follows from

Invariant 1

Agents decide. Deterministic Python enforces and scores. The ledger records. The extension only renders.

Four actors, four jobs, and none of them does another one's job. The reason is narrow and practical: language models are excellent at judgement and useless at grading themselves.

Ask a model to "rate your understanding of this ticket from 0 to 100" and it will say 92, because it knows 90 is usually the passing bar. That number looks like data, ends up on a dashboard, and someone makes a decision with it. So Docket never asks. It asks the model to enumerate the gaps and ambiguities — a task models genuinely do well — and then a Python function counts them and computes the score. The model never sees the scoring rule.

The same split appears at every stage, and once you see it you can predict how any new feature will be built:

Nobody has to trust a model's self-report, because nothing in the system ever reads one.

02The constraint that shaped everything

Why this is not a normal AI integration

Normally, connecting software to an AI model looks like this: get an API key, put it in an environment variable, make an HTTPS request. Three steps.

We cannot do any of them. The company's rule is:

Hard environmental constraint

GitHub Copilot, inside VS Code. Nothing else.

No API keys. No Copilot command-line tool. No other AI-powered IDE. No direct HTTP calls to any model provider, ever.

VS Code exposes an API to extensions called vscode.lm. An extension running inside a VS Code window can call it. Nothing else on the machine can — not a terminal script, not a cron job, not a server. That single fact means:

The only place in the universe where our code can reach a model is inside a running VS Code window.

Given that, there were two ways to build the product:

The decision that produced this architecture
OptionShapeConsequence
ABuild the whole product as a VS Code extension Hard to test. Cannot run headless. Tied to one editor permanently. Complete rewrite the day API access is approved.
B chosenBuild the product as ordinary Python, plus one thin extension whose only job is to relay model requests Testable headless. Editor-agnostic. The day API access lands, one line changes and the pipeline never notices.
Read this before you touch anything

vscode.lm is the primary and normal path. Running a ticket from VS Code needs no Docker, no ANTHROPIC_API_KEY, and no provider credential of any kind. Copilot in the editor is the whole model supply.

There is a second file, headless_gateway.py, that answers the identical protocol from a terminal using a locally signed-in CLI. It is an optional convenience for one developer's machine, it is never the recommended path, and nothing in the product requires it. If you find documentation implying headless is the normal way to run Docket, that documentation is wrong.

Part II

The LLM layer

How a language model actually behaves, how we reach one, what we send it, and what happens when it misbehaves. This is the part most people skip and then get wrong.

05How an LLM actually works

The mechanics you need before anything else makes sense

If you have never worked with a language model programmatically, four properties explain almost every design decision in the rest of this handbook.

1. It reads in tokens, not words

A model does not see letters or words. It chops text into chunks called tokens, each roughly three quarters of a word. "cat" is one token; "unbelievable" might be three. Two numbers follow you everywhere:

  • tokens_in — how much text we sent in this request
  • tokens_out — how much text came back

Tokens are the unit of both cost (providers bill per token) and capacity (every model has a maximum input size, called its context window). Docket checks the prompt size before sending and refuses an oversized one locally, with a clear message, rather than letting it fail at the provider with something opaque.

A token count we cannot get is null, never zero

Not every host implements token counting. When we cannot measure, we record null. Zero is a measurement; null means we do not know. A null is excluded from every sum and renders as a dash. A 0 would be averaged in as a free call — one JSON key away from a lie on the Cost tab.

2. It is completely stateless

This is the one that surprises people. The model remembers nothing between calls. There is no session, no conversation on the server. What feels like memory in a chat app is the client re-sending the entire conversation every single time.

So "context" is not a feature you switch on. Context is literally the bytes you chose to resend. Which leads directly to Docket's first load-bearing rule:

Try this one

Statelessness is easier to believe once you have seen it. In the playground, ask the same question twice and watch the answers differ — then look at the bridge and confirm there is nowhere for a conversation to be stored.

Rule: fresh message list per step

There is no session to save. Every step of the pipeline builds its request from scratch — the ticket dossier, the relevant slice of the repo map, the memory block — and sends that.

This is not an optimisation layered on top; it is the only thing the loop knows how to do. Long accumulating conversations degrade: the model re-reads its own dead ends and starts summarising instead of thinking. If gateway.js ever grows a conversation buffer, that guarantee is gone.

3. It is confidently wrong, especially about itself

A model will produce a plausible answer to anything, including questions it has no basis to answer. It will invent a module name, a function signature, or a vulnerability with exactly the same fluency as it reports a real one.

This is why the decide/enforce split from section 1 exists, and why the security scanner finds while the agent only triages. It is also why nothing a model writes ever enters Docket's memory without a human approving it.

4. The same input does not guarantee the same output

Model responses vary between runs. That is fine for judgement and fatal for scoring, which is the third argument for computing every gate verdict in code. It is also why agent prompts carry a version number and a content hash: when you compare two runs, you need to know whether the prompt was the same, because almost nothing else was.

06The wire protocol

Exactly what crosses the boundary, in both directions

The mental model is a restaurant. loop.py is the chef and writes order slips. gateway.js is the waiter and carries them. Copilot is the kitchen. The waiter never cooks, never reads the recipe, and does not know why this table ordered this dish.

We did not invent a protocol. We copied the shape of LSP (the Language Server Protocol, how your editor talks to autocomplete tooling) and MCP (the Model Context Protocol). You do not need to know either. The shape is: one JSON object per line, over standard input and standard output. If you have ever typed cmd_a | cmd_b in a terminal, that is the mechanism.

Try this one

You can watch this exact exchange happen on your own machine. python3 ask.py in the playground prints both directions of the wire with no VS Code involved, and pressing F5 turns it into a real Copilot call.

Concurrency: why every request carries an id

A single reader thread on the Python side reads replies and routes them by id into per-request queues. That is what lets three planning agents hold chats simultaneously over one pipe. Without ids, every call would have to complete before the next could start.

The capability contract

Before relying on anything, the loop asks what it is talking to. Two answers are load-bearing and hardcoded on this transport:

  • sessions: false — vscode.lm has no persistent conversation handle. Claiming otherwise would make the loop send conversational deltas into nothing.
  • cost_usd: "unavailable" — the string, not a number. Copilot exposes no billing data to extensions, so the Cost tab must show "Unavailable", never a confident $0.00.

Also reported: transport name and version, resolved provider, per-role requested-vs-effective models, whether token counting works (probed, not assumed), cache metrics, cancellation support, concurrency support, and whether provider tool calls are relayed (they are not).

07Model resolution

Roles, not model names

No agent file in this codebase names a model. Each declares a role, and the extension resolves that role against whatever the host actually exposes on this machine, in this company, today.

The four roles and their preference order
RolePrefersFalls back toWhy it exists
workersonnetgpt*, then anything The everyday workhorse: develop, spec, test-spec, QA, security.
judgeopussonnet, then anything Picks the winning plan and does blind review. Deliberately a different model from the planners: a judge sharing the planner's failure modes is not a judge.
second_plangpt* or o1/o3opus, then anything The dissenting opinion in a bake-off. A different vendor is the whole point — different training data, different blind spots.
cheaphaiku or minisonnet, then anything Triage and pre-screening: mutation explanations, retrospectives.

Why not just name the model? Because Copilot's model list changes — between companies, between subscription tiers, and between Tuesdays. A prompt file naming gpt-4-turbo breaks confusingly at 2am when that model disappears. A role resolves to the next best thing and carries on.

Drift is recorded, never silent

You can pin a model per role in config.json. If the pin does not resolve, Docket warns visibly and falls back — and records both the requested pin and the effective model. Without that pairing, a run's manifest could claim one model while another actually served every call, with no way to tell.

A placeholder still reading REPLACE_... is treated as no request at all, not as a failed one.

One more deliberate detail: selectChatModels returns an empty array for an unknown family rather than throwing. A hardcoded guess would therefore fail silently. So Docket never guesses — it asks the host what exists, matches by role, and raises a loud, actionable error when the host exposes nothing at all.

08What is actually in a prompt

The anatomy of one chat call

A chat request carries two strings: system and user. Here is what the pipeline assembles into them, freshly, on every single call.

The provenance stamp

Every event records which prompt produced it, in the form name@version:prompthash — for example spec@12:a1b2c3d4. The version is the number in the frontmatter; the hash is of the prompt body. Both matter: the version is what you reason about, the hash is what catches an edit where somebody forgot to bump the version.

Secret scrubbing happens on the way out

Anything written to the ledger is permanent, because the ledger is append-only. So every human-readable line leaving the gateway passes through a deterministic secret scrub first: PEM blocks, GitHub and Atlassian tokens, AWS key ids, JWTs, Authorization headers, credential-named key/value pairs, and credential-named command-line flags.

It is a shape scrub, not a judgement — no model, no heuristic scoring, no "looks secret-ish" rule. Over-redacting a diagnostic line is a cosmetic cost; under-redacting one is permanent.

09The agent tool loop

How an agent looks at the codebase

Some agents need to look at things before they can answer. They do not get filesystem access. They get a small vocabulary of tools, and a loop that runs them.

Why the budget is the design

Unbounded exploration is just "read the repository into context on every ticket" — roughly 200,000 tokens, and a model that summarises instead of thinking. Every tool-using agent therefore carries a step budget in its frontmatter. The cartographer gets 15 steps and a 60,000-character read cap; the lead gets 6; the planner 8; the developer 20; the fast-path scope agent gets exactly 1.

An earlier version used a fixed number of rounds ("here is the index, ask for files, now answer"). That was the same mistake one level up: the round count was a guess about how much looking is enough. Now the agent looks until it is satisfied, bounded by a budget.

A real failure this design came from

On one live run a shared read tool raised the same Python error on every call. The loop turned each failure into a prose line in the transcript, and the agents kept paying for looks: the cartographer spent 9, the lead 3, the planner 6 — and then the planner wrote a plan from guessed API facts.

Hence the containment rule in the figure. Repeated identical tool failure is an infrastructure problem, and no amount of retrying fixes it.

10Errors, retries and budgets

What happens when the model layer misbehaves

The typed error taxonomy

Every failure crossing the gateway boundary used to be one shape: a string. So the loop could not tell "the provider refused this prompt" from "the quota is gone" from "the user pressed Stop". Now every error carries a type, derived from exactly two sources — what we did, and the provider's machine-readable code. Never the message text, which is localised and rewritten between releases.

Error types and how each is treated
TypeMeansRetryable
provider_refusedContent filter or policy refusalNo — permanent
auth_failedNot signed in, or no permissionNo — a human must act
no_modelsNo models visible to extensions at allNo — local setup problem
model_not_foundThe requested model does not existNo
quota_exceededRate limited or out of quotaYes
timeoutThe request exceeded the per-call timerYes
empty_responseThe stream yielded no text at allYes — one hiccup is worth a retry
prompt_too_largeRejected locally before sendingNo — the calling stage must send less

provider_errorA code the table does not recogniseNo — visibly unclassified beats confidently wrong
Two deliberate refusals to be clever

An empty stream is an error, not a success. Handing back a successful empty answer makes the calling stage fail later, parsing an empty plan somewhere far from the cause.

An unknown provider code stays unknown. A host that ships quota exhaustion under some code we have never seen must surface as an unknown, not as a mislabelled refusal.

Retry policy

Three attempts, with linearly growing backoff. Retries apply only to transient conditions: rate limits, timeouts, empty responses, overload. A dead pipe, a protocol desync, a startup incompatibility, or a policy budget refusal all re-raise immediately — retrying those can only make things worse or burn quota on a doomed request.

Timeouts

  • Per model request: 600 seconds by default, configurable, 0 disables it. Deliberately under the loop's own reply timeout so the loop learns a typed retryable timeout rather than an unexplainable desync.
  • Per reply, loop side: 900 seconds. A gateway that stays alive but drops one reply must not hang the run forever.
  • Stop grace: 10 seconds for a stopped run to exit on its own before its whole process tree is killed.

Budgets

Two independent brakes, both computed from ledger sums and never self-reported:

  • Dollar budget per ticket — and because vscode.lm exposes no billing at all, cost is derived from an operator-declared price map in config.json. No price map means no cost, which renders as a dash. Never an invented zero.
  • Token cap per run — checked before the expensive stages. Exceeding it is a clean halt, and Resume Run continues from what already passed rather than paying for the whole pipeline again.

agents/reviewer.mdthe complete shape

reasoning, or any...

Optional frontmatter keys for agents that need to look at things: tools (which of list, grep, read, replace, write, test it may use), max_steps, and max_chars_read.

Why a file and not a Python class

  1. You will edit these constantly. Every real ticket teaches an agent something. That should not require opening a .py file, understanding the surrounding plumbing, and risking a syntax error in production logic.
  2. The version number makes evaluation real. Every event records the agent's version, so "did that prompt change help?" is a query against the ledger instead of an argument.
Enforced, not merely requested

Three rules the loader checks: name must match the filename; name, version and model have no defaults (a silently defaulted agent stamps as name@0 and every eval built on it is quietly wrong); and model must be one of the four roles. An agent file naming a vendor or a concrete model has hardcoded a runtime decision, and is rejected.

A missing agent file raises. There is no built-in fallback prompt anywhere in the system.

What is deliberately not in the file: the loop. Parsing the reply, running a tool, feeding the result back, counting the budget, recovering from a malformed turn — that is Python. VS Code's own agent files can skip it because VS Code's agent mode is the loop. We only have a raw model provider, so the harness is ours.

the file  = what the agent is told, and which model role it gets   <- yours

13Agent memory

How an agent learns without editing itself

There are two learning targets, and they are different in kind:

  • context/<project>.md — facts about the project: what it is, where things are. Every agent reads it.
  • memory/<project>/<agent>.md — craft lessons for one agent on one project. Only that agent reads it.
memory/data_project/planner.mda real example

The one loop that must stay open

An agent that can silently edit its own instructions is unbounded. So the retro agent may only propose a lesson. It lands in a queue. A human approves it. Only then is it appended under ## Learned from tickets, and folded into that agent's prompt from the next run onward.

The same applies to the project context file: the drafter writes it with a reviewed: false marker, and it does not count as ratified until a human removes that line.

Part IV

The pipeline

The assembly line itself: what runs, in what order, what stops it, and what keeps it from damaging your repository.

14Stages, gates and three vocabularies

The thing that confuses everyone exactly once

A stage is a step of work. A gate is a checkpoint at the end of a stage that decides whether the run may continue. Think of a bottling plant: the line moves the bottle along, and sensors reject bad ones.

Three naming vocabularies, and they disagree

This is a genuine wart in the codebase, not a documentation error. There are three lists of names in play:

The three vocabulariesread the source list; never type a name from memory
1. loop.py STAGE_SEQ      the 9 stage names the run monitor uses
   comprehension, blast_radius, plan, frozen_tests, develop,
   blind_review, security_snyk, qa_e2e, mutation

2. governor.py PIPELINE   8 entries, DIFFERENT stage spellings
   comprehension, plan, test-spec, developer, reviewer,
   security, qa, mutation
   (no blast_radius here, because it has no gate)

3. ledger.py GATES        the 8 gate names written to the database
   comprehension, plan_approval, frozen_tests, blind_review,
   unit_tests, security_snyk, mutation, qa_e2e

Why this matters on day one: if you write anything that displays a run, look up gate rows using list 3. Getting this wrong once made the entire Gates tab render blank — the code searched for gate rows using stage names, found nothing, and reported nothing, silently.

Do not rename anything casually. The ledger is append-only and full of historical rows using the current spellings.

The schema enforces the reason requirement: a row whose outcome is unknown or skipped with a null unknown_reason is rejected by a CHECK constraint. Honesty is a database constraint here, not a convention.

A halt is the product working

If the comprehension gate stops to ask the ticket author a clarifying question, that is success, not failure. The run outcome is escalated, it needs a human, and it must never be coloured red or counted as a defect anywhere.

A mutant the tests still pass is a survivor. The gate is the computed kill rate. The mutation agent only explains what each survivor means.

The low-risk fast path

Not every ticket deserves nine full stages. When deterministic checks measure a ticket as small — clean comprehension, at most four testable criteria, naming at most three files that actually exist, no danger zone, no forced bake-off — the blast radius and the implementation plan come out of one scope_plan turn as two separately validated artifacts.

This exists because a live run once spent nine model calls before development on exactly such a ticket. The setting is auto by default; always forces it and records which signals it overrode. One signal is never overridable: a pending plan-change request means a human already asked for a different plan, and that always takes the slow path.

Repair rounds

A failed stage does not necessarily end the run. Bounded repair loops re-run just the failed stage plus a re-review, which is far cheaper than a fresh run of five stages. The counts are configuration, and there is a switch controlling whether a repaired stage goes back through blind review before re-testing rather than skipping straight to QA.

17Safety machinery

What stops an AI-driven pipeline from damaging your repository

The blast radius

The lead declares: this ticket may touch these files and no others. That declaration is not advice. It is checked against the repo map before anyone believes it, and then it becomes a boundary that a hook enforces. An edit outside it is blocked, not warned about.

Every pipeline can say what it plans to change. Almost none can say what it has agreed not to change — and that is the more useful half. "The developer touched a file nobody authorised" is normally something you find out in code review, or in production.

Widening the radius is allowed, and it is an event: the developer must ask, the lead approves or refuses, and the ledger records that it happened. A ticket that widened three times is a ticket whose plan was wrong, and next quarter that is a query rather than an argument.

The checkpointer

A shadow git repository that lives outside the project's real .git and never touches it:

checkpointer.pythe shadow repo
shadow git dir : cache/<project>/<ticket>/checkpoints.git   (GIT_DIR)
work tree      : the live project repo root                 (GIT_WORK_TREE)
scope          : only the blast-radius paths are ever tracked

One commit per task. Rollback restores tracked files to a chosen checkpoint and physically removes anything created since. The verdict "are we back to pristine?" is computed by git itself — it cannot be guessed, and no model is involved. It also produces the exact pristine-to-final diff the blind reviewer sees.

Command containment

A git worktree is source isolation, not an execution sandbox. Until a real OS-level sandbox exists, every model-influenced command runs through one function that enforces:

  • List-form commands only. A string command is refused outright, so no shell ever interprets model-written text.
  • An executable allowlist. The program's basename must be allowed (python and pytest by default). Operators extend the list. Models never can.

Stopping and resuming

Stop Run cancels the shared cancellation token, which cancels every in-flight model request, then closes the pipe and gives the process tree a grace period before killing it outright (on POSIX the child gets its own process group, because test-framework grandchildren survive a plain kill and keep file locks). Long local loops such as mutation poll for pipe closure between iterations so a stop lands in seconds rather than after the whole stage. A stopped run parks in a resumable state; Resume Run continues from the last gate that passed.

Why artifacts are files and not database rows

Prose reviews, plans and HTML reports stay on disk. The ledger records that each exists, which run made it, which agent wrote it, and its sha256. The two halves do different jobs and neither replaces the other:

  • The folder holds artifacts humans read. A peer review is prose. A plan is prose. An HTML report is two megabytes. None of that belongs in SQLite.
  • The ledger answers queries. "Which gate caught the most defects across 200 tickets?" is not a thing a folder can answer.
Where the AI's code actually appears

In your real working tree, in the sibling project, in the normal place. You review it with git diff exactly as you would review a colleague's work. There is no hidden staging area. The shadow repo is only a safety net; it never appears in your history and never interferes with your branches.

21The finding taxonomy

What Docket is allowed to claim

This exists because the temptation to overclaim is enormous. A surviving mutant feels like a bug. A failing test feels like proof. Neither is.

Invariant 10

A killed or surviving mutant is evidence, not a verdict. DOCKET_FOUND_IT requires a deterministic reproducer plus an independent oracle — never the code asserting on itself.

Every verdict, weakest claim to strongest
VerdictRequires
NO_FINDINGEverything green. The does-not-cry-wolf case, and it must be comfortably reachable.
HARNESS_FAILUREA suite that did not run, a failed baseline, or a mutation error. Our problem, not the code's.
TEST_GAP_FOUNDSurviving mutants. The tests would miss a real bug of that shape.
REGRESSION_RISK_FOUNDThe shipped tests fail against the shipped code under our harness.
SPEC_GAP_FOUNDA genuine failure, but no independent source of truth about what correct behaviour is. The ticket was ambiguous.
DOCKET_FOUND_ITA deterministic reproducer and a declared independent oracle. The only verdict that asserts a real defect.

Where multiple findings co-occur they are all kept in a list, and the reported verdict is the highest-priority one. The oracle priority order, from strongest, is: an executable contract, an accepted ticket criterion, an API or schema definition, a designated authoritative behaviour, a human clarification — and if none of those exist, the honest answer is SPEC_GAP_FOUND.

Part VI

Memory

How Docket remembers across tickets, and why there is no vector database anywhere in it.

22The knowledge graph

Recall is a query, not a search

Most systems that "remember" use a vector database: turn text into numbers, store them, search for similar numbers later. Docket does not have one, and that is a decision rather than an omission.

The reasoning: the ledger already records everything that ever happened. So memory is not a storage problem, it is a recall problem — and recall is a SQL query. Deterministic, capped, and every line can cite the exact run it came from, so any claim in a prompt is checkable against the record.

The whole argument in one line

A memory that can hallucinate is worse than no memory. This one cannot, because no model ever writes into it.

Plane A — the typed graph

A real table. Six edge types — touched, blocked, flagged, superseded, learned_from, co_changed_with — over seven node kinds: ticket, file, agent, plan, finding, learning, run.

Edges are never written by hand; they are the fourth step of section 19's transaction. Today exactly one production path produces them: the lead declaring its blast radius. So an edge means something precise. It does not mean "this file was changed". It means "the lead said it intended to touch this file, on this run, and recorded a reason". Keep that distinction in mind when you read the map.

Plane B — the repo map

A script walks the tree and parses ASTs: which classes exist, what they inherit, where the config files and jars are. There is deliberately no LLM in that script. Facts are deterministic, and a dictionary lookup beats a model's guess because it cannot invent a module that is not there.

The clever part is mined from git history: which files change together. That catches coupling imports cannot see — a parser and its fixture, a config and the code that reads it. Commits touching more than twelve files are excluded, because a large merge couples everything to everything and tells you nothing.

That index is then handed to the cartographer as a free first tool result it may ignore, never as an answer. Facts from the script; judgement from the model.

Why this file has no heuristics in it

An earlier version grouped modules by shared base class and naming convention. On the first real 24-module framework it met, it confidently reported a family called "Static" and missed the actual extension pattern entirely. That was not under-tuning. "How do you add a source type?" has a different answer in every repository — base class, registry, entry point, decorator, config dispatch, or nothing but convention. Encode that guess as an if-statement and you have built something that works on the repository you imagined.

Plane C, and what comes back

Craft lessons in markdown, covered in section 13. All three planes come back as one capped text block at the top of a stage's prompt:

knowledge.recall()what an agent actually receives
=== PROJECT MEMORY (computed from the ledger - every line cites its run;
    verify against the tree before relying on it) ===

PROJECT HUB FILES (most consulted by past agents - look here first): ...
RECENT WORK IN THIS PROJECT (latest run per ticket, state from the gates table):
THESE FILES WERE WORKED RECENTLY (the lead's recorded reason, from that run):
ESCAPED DEFECTS (bugs the pipeline missed - the strongest signal memory carries):

It never raises. An unreadable ledger returns an empty string, because advice must never be able to block a run. And for the UI, one Python projection computes everything including the layout coordinates — the Knowledge Map webview draws SVG from positions Python calculated. No D3, no CDN, no arithmetic in the browser.

26The ten invariants

How this codebase stays honest

Every module ships a --self-test. There are 95 Python self-tests and 24 JavaScript check suites registered in one runner, and a new module is expected to join them.

The lie this runner exists to prevent

A check that silently cannot run is a failure, not a skip. "Green because nothing executed" is the exact failure mode the explicit registry guards against: a module deleted or renamed without updating the registry fails loudly here instead of quietly dropping out of coverage.

Phase 3 needs Node on your PATH

Phase 3 is the JavaScript half of the ladder, and it shells out to node. If Node is missing, the runner does not skip — it reports a failure that names itself:

"node not found on PATH — this repository's own JS checks cannot run, so this ladder is incomplete; that is a failure of the test ladder, not of Docket. Running Docket needs no system node: VS Code's extension host provides the runtime."

Note that this is reported as a failure (exit 1), not as the third state unavailable (exit 3). The distinction is deliberate: unavailable is for a capability the machine legitimately may not offer — serve.py needing to bind a local port, which a sandbox can refuse. A developer machine without Node is an incomplete developer machine, so it is a real failure with a real fix.

What to do when it stops and you do not know why

Start by working out which kind of problem you have, because the three are diagnosed in completely different places.

Read the stop reason before anything else

Step 2: read the channel log

It is registered as an evidence artifact, so it also shows up in the Artifacts tab and the run drill-down, and can be attached to the ticket. This is deliberately kept out of ledger rows and out of the dashboard inline content — it is a file, because it is prose.

Step 3: if it is the bridge, trace the wire

Wire-level tracingenvironment variable
DOCKET_TRANSPORT_DEBUG=1 python3 loop.py ...

# prints one stderr line per reply id, and a loud line if the
# reader thread dies - which is the failure that otherwise turns
# every later request into a silent forever-hang.

The three bridge failures worth recognising on sight:

  • "gateway closed the pipe" — the VS Code window closed or the extension crashed. Not retryable.
  • "no reply for request N after 900s" — the gateway is alive but dropped a reply. A real desync, surfaced loudly instead of hanging forever.
  • "gateway sent non-JSON" — something printed to stdout that was not protocol. Almost always a stray print() in Python. Remember: stdout is the wire.

Step 4: re-run cheaply

Resume rather than restartthis is the one that saves money

# stages that already went green

# force a specific model per role, without editing config.json
python3 loop.py --ticket ABC-1 --models '{"worker": "gpt-4o"}'
Two habits worth forming early

Never run the check ladder while a real run is in flight. They share the workbench ledger. A live run writing to it mid-self-test has produced a phantom red before, and it cost real time to diagnose.

Reach for --resume before you re-run. A fresh run of five stages is roughly two hundred thousand tokens; a repair round is a fraction of that.

31Recipes: how do I add...

The five things you will actually be asked to do

Add a new agent

  1. Create agents/<name>.md. The name in the frontmatter must match the filename.
  2. Set version: 1 and a model role — one of worker, judge, second_plan, cheap. Never a model id; the loader rejects a vendor name.
  3. If it needs to look at files, add tools: and a max_steps: budget. Unbounded exploration is a design bug, not a convenience.
  4. Load it with roster.load("<name>", workbench). There is no registration list; a missing file raises rather than falling back.
  5. Keep the loop in Python. The file says what; the harness says how.
When you EDIT an agent

Bump version. Every ledger row is stamped name@version:prompthash, and every evaluation is built on that stamp. Editing the body without bumping the number silently invalidates the comparison — the hash will differ from the recorded one and nothing will tell you.

Add a new gate

  1. Add the name to ledger.GATES and to the gate_name CHECK constraint in schema.sql. They must agree; a self-test proves it.
  2. Add an entry to governor.PIPELINE with its stage, gate and requires. If the gate is optional, no later stage may require it.
  3. Write the verdict in deterministic Python. If a model is deciding, you have built something else.
  4. Record it with the three-state vocabulary. An unknown or skipped row must carry an unknown_reason — the schema rejects it otherwise.
  5. Put what it caught into details_json, so the Gates drill-down can show it.
  6. Add a config block under gates with an enabled flag, so it can ship switched off.

Add a VS Code command

  1. Declare it in extension/package.json under contributes.commands. That file is the only authority on the list.
  2. Create extension/src/<feature>.js. One module per concern.
  3. Add a require and a registerCommand line to extension.js — and nothing else. It never grows sideways.
  4. If it needs data, spawn Python for it. The extension renders; it does not compute.
  5. Add a preview_<feature>.js --check harness and register it in run_all_checks.py.

Add a dashboard tab

  1. Add the numbers to the projection in payload_builder.py. It is the only file that may touch SQLite.
  2. Render from the payload in dashboard/app.js. The webview does arithmetic on nothing.
  3. Render a missing value as a dash. Never zero. Never $0.00.
  4. Check it in all three hosts — report.py, serve.py, and the webview — because they share one payload but not one shell.

Add any new module

  1. Put it in the same folder as loop.py and mutation.py. Confirm which folder that is first; two copies in two folders is a recurring, expensive bug in this repository's history.
  2. Give it a --self-test that points at the real agent files and fixtures, never inlined copies.
  3. Register it in run_all_checks.py. An unregistered module silently drops out of coverage, which is the exact lie the explicit registry exists to prevent.
  4. Obey the exit contract: 0 passed, 1 failed, 3 could not run here.
  5. Scan it for any character above 127 before you commit.

The shape of a run's spend

Spend is not evenly distributed. The develop stage dominates — it is the one with write tools, a 20-step budget, and repair rounds behind it. Everything before development is comparatively cheap, which is precisely why the envelope caps it separately.

The envelope caps tokens and requests, never response time. Docket cannot promise another service's latency, so timing targets are proved offline against a declared latency model and only reported on a live run.

33Security and trust

What is enforced, and what honestly is not

What is trusted, and what is not

The rule to internalise: anything a model wrote, and anything that reached the model from outside, is untrusted. That includes ticket text from Jira, README files, and the output of any tool an agent ran.

Be honest about this one

Treating Jira text, READMEs and tool output as untrusted, with prompt-injection fixtures to prove it, is on the roadmap — it is not built today. It is named in the architecture-review north star alongside the execution sandbox.

So do not tell anyone Docket is hardened against prompt injection. What exists today is containment of what a model can do, not validation of what it reads.

What is genuinely enforced

Controls that exist and are tested
ControlWhat it does
List-form argv only A string command is refused, so no shell ever interprets model text. Shell metacharacters in arguments are inert bytes.
Executable allowlist argv[0]'s basename must be allowed. Shells are not on the list, so bash -c ... dies at the policy rather than running.
Path policy An argument resolving outside every allowed root is refused — covers ../ traversal, absolute escapes, and symlink escapes.
Sanitized environment Allowlisted names only, and anything matching KEY / TOKEN / SECRET / PASSW / CREDENTIAL / AUTH is always dropped, allowlisted or not.
Process-tree kill Timeouts kill the whole group, with a two-stage reap for unreapable grandchildren. Test-framework JVMs survive a plain kill and keep file locks.
The blast radius Writes outside the declared file list are blocked, not warned about.
Secret scrubbing Every human-readable line leaving the gateway is scrubbed before it can reach the append-only ledger, where it would be permanent.
Audit trail Every contained call and its outcome is recorded. A refusal returns code 126 with a loud marker; nothing is swallowed.

What is stated as NOT enforceable

The containment module names its own limits rather than implying coverage it does not have:

  • No network isolation. There is no sandbox on a bare macOS host, so the capability is declared False — and the untrusted-project profile therefore fails closed rather than running without it.
  • No syscall-level write containment. Writes are held by the tool-layer radius guard, the checkpointer's scope, and the path policy. A compiled child could still write elsewhere. That residual risk is exactly why untrusted projects refuse to run at all.
The pattern worth copying

Notice what that module does: it lists what it enforces, and then lists what it cannot, in the same breath. A security control that overstates itself is worse than none, because people stop checking.

Credentials

Jira credentials live in .local/docket-runtime.env, which is gitignored. A file beats system environment variables here for a practical reason: the extension host inherits the environment from whenever VS Code was launched, which is often stale. Custom field values never leave Jira — only field keys travel.

Read this first — it explains every step below

vscode.lm is only reachable from inside a running VS Code extension host. Not from a terminal, not from a cron job, not from a server. No flag, token or setting changes this — it is how the API works.

So you cannot point ask.py at Copilot directly. You have to put it behind an extension. That is the whole reason the bridge exists, and the whole reason Docket is shaped the way it is.

What you need before you start

  • VS Code, version 1.95 or newer.
  • GitHub Copilot installed and signed in. Check the account icon in the bottom-left of VS Code. This is the part that most often is not ready.
  • Python 3 on your PATH. Nothing else — no pip install, no npm install, no build step.

The one thing to understand: there will be TWO windows

This is where almost everyone gets stuck, so it is worth thirty seconds. Pressing F5 does not run your code in the window you are looking at. It opens a second VS Code window with your extension loaded into it. You edit in the first window and you run in the second.

What just happened

Window 2 spawned ask.py as a child process with a pipe. Python wrote {"id":1,"method":"chat",...} to its stdout. The bridge read that line, called vscode.lm, and wrote the answer back to Python's stdin.

Your Python owned the logic; the bridge only carried messages. That is the identical arrangement loop.py and gateway.js use for a real ticket — just with 20,000 fewer lines on the Python side.

Things worth trying

  • Rebuild the reviewer. Put a reviewer brief in SYSTEM and a diff in PROMPT. That is Docket's reviewer agent in miniature (section 12).
  • Run a real agent by hand. Open any file in agents/, copy its body into SYSTEM, and you are running the genuine article — same prompt, same model.
  • Ask the same question twice. The answers differ. That non-determinism is the third argument for computing every gate verdict in code (section 5).
  • Send something enormous. Watch it fail on the context window — then note that the real gateway catches that before sending, with a message that names the limit (section 6).

What the playground leaves out on purpose

The real gateway.js is 1,585 lines because it also handles role resolution, concurrent requests routed by id, a typed error taxonomy, retries and timeouts and cancellation, secret scrubbing before anything can reach the append-only ledger, and a ten-field capability probe.

Everything else — the protocol, the fresh message list per call, the null-not-zero token handling, the stdout-is-the-wire rule — is the same in the playground as in production. Sections 6 to 10 have the full version.
